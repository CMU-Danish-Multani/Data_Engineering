1. Brief

In short: we pull six public data feeds about five AI infrastructure companies, keep every file exactly as downloaded, put numbers in PostgreSQL and text in MongoDB, and let a dashboard and an LLM assistant read both: 16 KPIs from PostgreSQL, searchable release and call text from MongoDB.

High-level design (HLD)

The whole system on one page. Read it left to right: get the data, keep the original, organize it by kind, use it.

CompaniesMicrosoft, Alphabet, Amazon, Meta (the largest buyers of AI computing) and NVIDIA (the largest supplier of AI chips)
Problem statementHow can retail investors compare companies using financial performance, institutional investment activity, and qualitative information?
Sources6 feeds from 3 providers: SEC EDGAR (4 feeds), Yahoo Finance, Alpha Vantage
StorageAmazon S3 (original files), PostgreSQL (the numbers: raw tables, star schema, KPI views), MongoDB (the text: releases, transcripts, and their embeddings, searched with Atlas Vector Search)
Output16 KPIs per company per quarter and per year (PostgreSQL views) and searchable management commentary (MongoDB), read by a dashboard and an LLM assistant

3. Data storage

In short: S3 keeps every original file. PostgreSQL keeps the numbers: raw tables first, then the cleaned layers. MongoDB keeps the text and its embeddings, and applications read it directly. Raw data is never edited.

3.1 Which store holds what, and why

StoreWhat lives thereWhy this store
Amazon S3
s3://team8-stock-intel/raw/		Every downloaded file: companyfacts JSON, submissions JSON, release HTML, 13F ZIPs, price CSVs, transcript JSONCheap, durable, shared by all four members. Any later step reruns from the original file without calling the APIs again, which matters with a 25-call daily limit.
PostgreSQL rawXBRL company facts (one JSON value per company), prices, 13F tables, company seed listEvery number here ends up in a KPI, so it goes where joins, keys and SQL math are. Raw tables keep text and JSON with no constraints, so no problem record is rejected at load.
PostgreSQL staging, core, serving, opsCleaning work, the star schema, KPI views, logsThe retrieval point for numbers: the dashboard and the assistant's SQL tool read the serving views (sections 4 and 6).
MongoDB stock_intelEarnings releases, call transcripts, and their passages with embeddingsThe retrieval point for text. Each document is kept whole, in a shape that varies by company and quarter. Atlas Vector Search finds passages by meaning inside the same database, so the dashboard and the assistant read text straight from MongoDB (section 5).

The rule: numbers in PostgreSQL, text in MongoDB. Each kind of data goes to the database that is good at it, and is read from there. Numbers in MongoDB would lose the joins and constraints the KPIs need. Long text and embeddings in PostgreSQL would split each document into rows and need the pgvector extension. S3 alone would leave nothing queryable.

4. Data transformation

In short: raw data is flattened, parsed and cleaned in the staging schema, checked, and then upserted into the core star schema, where every table has types, keys and constraints. Cleaning is done in SQL; SQL JSON functions flatten XBRL; Python only parses release text.

4.1 Flattening XBRL inside PostgreSQL

Flattening turns one nested JSON value into many flat rows, one row per reported value. Each CROSS JOIN LATERAL opens one level of nesting.

INSERT INTO staging.xbrl_facts
SELECT r.cik, tx.key AS taxonomy, c.key AS tag, u.key AS unit,
       v ->> 'start' AS period_start, v ->> 'end' AS period_end, v ->> 'val' AS value,
       v ->> 'accn' AS accession_no, v ->> 'fy' AS fiscal_year, v ->> 'fp' AS fiscal_period,
       v ->> 'form' AS form, v ->> 'filed' AS filed_date, r.load_id
FROM raw.xbrl_companyfacts r
CROSS JOIN LATERAL jsonb_each(r.payload -> 'facts') tx         -- us-gaap, dei
CROSS JOIN LATERAL jsonb_each(tx.value) c                      -- one entry per concept
CROSS JOIN LATERAL jsonb_each(c.value -> 'units') u            -- USD, shares, USD/shares
CROSS JOIN LATERAL jsonb_array_elements(u.value) v             -- one row per reported value
WHERE c.key IN (SELECT tag FROM ops.xbrl_concept_map)
  AND r.load_id = (SELECT max(x.load_id) FROM raw.xbrl_companyfacts x WHERE x.cik = r.cik);

Only the newest file per company is read. Shares and per-share values come out of the same query, with unit shares or USD/shares.

5. Vector database (MongoDB)

In short: release and call text is cut into passages of about 500 tokens. Each passage is turned into a list of numbers that captures its meaning (an embedding) and stored as one document in the MongoDB collection document_chunks, next to the documents it came from. An Atlas Vector Search index finds passages by meaning. Numbers never come from here: they come from PostgreSQL.

5.1 What goes into the vector collection

source_typeComes fromHow it is cut into chunksWhy it is useful
transcriptMongoDB earnings_transcriptsOne chunk per speaker turn; long turns cut at about 500 tokens with a short overlap; speaker keptManagement's own words, and analysts' questions on AI spending
earnings_releaseMongoDB earnings_releasesSplit by paragraph and section heading; tables are not embedded (their numbers are in SQL)Official statements about products and outlook

Not embedded: XBRL facts, prices, 13F and KPI values. They are numbers, so SQL answers them exactly.

  { "type": "vector", "path": "embedding", "numDimensions": 384, "similarity": "cosine" },
  { "type": "filter", "path": "ticker" },
  { "type": "filter", "path": "fiscal_year" },
  { "type": "filter", "path": "fiscal_quarter" },
  { "type": "filter", "path": "source_type" } ] }

// query: the 8 passages closest to the question, Microsoft only, fiscal 2026 onward
db.document_chunks.aggregate([
  { $vectorSearch: { index: "chunks_vector", path: "embedding",
      queryVector: <embedding of the question>, numCandidates: 200, limit: 8,
      filter: { ticker: "MSFT", fiscal_year: { $gte: 2026 } } } },
  { $project: { _id: 0, text: 1, ticker: 1, fiscal_year: 1, fiscal_quarter: 1,
                source_id: 1, speaker: 1, score: { $meta: "vectorSearchScore" } } }
])

numDimensions must match the chosen model (384 or 1,536). A field can be used in the search filter only if the index declares it as a filter field.

5.3 How the assistant answers a question

Why the vectors live in MongoDB. The text is already in MongoDB, so each chunk sits next to the document it came from, and the vector index runs on the same cluster with no extra extension or service. The cost: one query can no longer join a passage to a KPI. The assistant calls the two tools separately and matches the results on ticker and fiscal quarter.

Size check. The free Atlas cluster holds 0.5 GB, indexes included. Expected, not measured: about 5,000 chunks (roughly 40 per call and 10 per release, times 100 each). At about 13 bytes per stored number, embeddings take about 25 MB with 384 numbers or 100 MB with 1,536, plus a few tens of MB of text. Real sizes are logged at the first load. If they come near the limit, the fix is a paid tier or storing embeddings in compact binary form.

6. Data serving

In short: SQL views turn the core star schema into analysis-ready tables: one row per company per quarter (or year), one column per KPI. Every view has the same key columns, so they join and filter the same way. Views always show the latest load. Serving is the retrieval point for numbers; MongoDB (section 5) is the retrieval point for text.

How a view is written: Table 1

CREATE VIEW serving.financial_metrics_quarterly AS
WITH q AS (                                   -- pivot: one row per company and quarter, one column per input
  SELECT f.company_id, f.period_id,
         MAX(f.value) FILTER (WHERE m.metric_code = 'revenue')             AS revenue,
         MAX(f.value) FILTER (WHERE m.metric_code = 'capex')               AS capex,
         MAX(f.value) FILTER (WHERE m.metric_code = 'operating_income')    AS operating_income,
         MAX(f.value) FILTER (WHERE m.metric_code = 'operating_cash_flow') AS operating_cash_flow
  FROM core.fact_reported_metric f
  JOIN core.dim_metric m USING (metric_id)
  GROUP BY f.company_id, f.period_id
)
SELECT c.company_name, c.ticker, p.fiscal_year, p.fiscal_quarter, p.period_end,
       p.calendar_year, p.calendar_quarter,
       q.revenue                                        AS revenue_usd,
       100 * (q.revenue / NULLIF(ly.revenue, 0) - 1)    AS revenue_growth_yoy_pct,
       q.capex                                          AS capex_usd,
       100 * (q.capex / NULLIF(ly.capex, 0) - 1)        AS capex_growth_yoy_pct,
       100 * q.capex / NULLIF(q.revenue, 0)             AS capex_to_revenue_pct,
       100 * q.operating_income / NULLIF(q.revenue, 0)  AS operating_margin_pct,
       q.operating_cash_flow - q.capex                  AS free_cash_flow_usd
FROM q
JOIN core.dim_fiscal_period p ON p.period_id = q.period_id
JOIN core.dim_company c       ON c.company_id = q.company_id
LEFT JOIN core.dim_fiscal_period pl                     -- same fiscal quarter, one year earlier
       ON pl.company_id = p.company_id
      AND pl.fiscal_year = p.fiscal_year - 1
      AND pl.fiscal_quarter = p.fiscal_quarter
LEFT JOIN q ly ON ly.period_id = pl.period_id;

Growth joins to last year's quarter by key, so a missing quarter gives one null instead of shifting every later comparison. _pct columns hold percentages (12.5, not 0.125), and NULLIF turns a zero denominator into null. The other views follow the same pattern; the two valuation views are materialized and refreshed after each price load.

8. Operating the pipeline

In short: cron runs each job on its source's schedule; every run is logged; every number can be traced back to its file; reruns are safe; only pipeline jobs can write.

8.2 Tracing any number back to its source

Text has the same trail. A chunk's source_id points to its MongoDB document, whose s3_path points to the original file.

Reruns are safe. Every write is an upsert on a natural key (accession number; ticker and date; manager and quarter; chunk _id), so a second run changes no counts. A failed run writes nothing to core, and the next scheduled run starts from the same watermark.
